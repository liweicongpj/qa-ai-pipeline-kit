# 大批资料与检索

真实项目的资料量很大：几百份策划案、几千张配置表、成千上万条缺陷。这些资料放不进一次提示词，也不适合复制进工作区。框架的做法是：**资料留在原处，在工作区里建索引，按需检索**。

## 两层知识

| 层 | 放什么 | 谁维护 | 进 git |
|---|---|---|---|
| 资料索引（`.qa/index.sqlite`） | 全部原始资料：策划案、配置表、历史缺陷；本工作区做过的需求和登记的缺陷（自动加，不用登记） | 框架自动建、自动增量更新 | 不进（随时可重建） |
| 知识库（`wiki/`） | 精华：每个模块的核心规则和计算口径、耦合关系表、风险清单 | AI 按模块分批整理，人审 | 进 |

生成测试点时两层一起用：知识库给“这个模块怎么运作、跟谁共用数值、哪些地方容易出事”，检索给“这次需求相关的原文段落、以前同模块需求定下的规则、同类历史缺陷、要用的配置表”。

知识库里**不抄配置数值**，只写规则、口径和“数值在哪张表哪个字段”（例如“见 economy/gear.rod 的 unlockPondLv、price”）：配置一改，抄进去的数值就过时了；要用数值时 `cfg show` 现查。

两层怎么保持同步：

| 什么变了 | 框架怎么提醒 | 怎么做 |
|---|---|---|
| 资料文件夹里加了或改了文件 | `status`：资料索引要更新 | `qa.py index` |
| 文档类资料变了（知识库提交以后） | `status`：知识库可能要更新 | `qa.py prompt wiki-update`，AI 用 `index show` 读新文档，人审后 `wiki commit` |
| 需求定稿了 | `accept` 和 `status`：新规则还没并进知识库 | `qa.py prompt wiki-merge R002`，人审后 `wiki commit --merged R002` |
| 发现漏测缺陷 | `status`：待回流 | `qa.py prompt feedback`，规律写回风险清单、耦合表 |

知识库是在登记资料之前提交的老工作区，第一次 `qa.py index` 时会把当时的文档记为对照基线，之后的变化才会提醒。

## 三类资料，三种查法

| 资料 | 支持的格式 | 怎么查 | 为什么这样 |
|---|---|---|---|
| 策划案等文档（`--kind doc`） | Word、Excel、网页、PDF、Markdown、文本；在线文档（飞书、Confluence、腾讯文档）先导出成这些格式 | 按标题切段，`search` 检索：关键词检索 + 可选向量检索，两路合并 | 规则藏在长文档里，要按内容找段落 |
| 配置表（`--kind config`） | Excel、CSV、JSON。Excel / CSV 自动识别“字段名 / 类型 / 中文注释”几行表头；JSON 按结构拆表（见下） | `cfg find` 按表名、字段、注释、取值找表；`cfg show` 精确查行 | 数值不能让模型“搜”，容易张冠李戴，要精确读 |
| 历史缺陷（`--kind defect`） | 禅道、TAPD、Jira、飞书项目、自建系统导出的 CSV / Excel | `history find` 检索（可按模块筛），`history stats` 统计 | 自动识别列名；认不出的在 `qa.config.json` 的 `defect_columns` 里指定 |

另外两类工作区自带、不用登记，`qa.py index` 时自动建：

| 资料名 | 内容 | 用处 |
|---|---|---|
| 本工作区需求 | 每个需求的 需求.md 和 最终测试点.md | 新需求另起文档、或只在禅道提了需求单时，以后同模块的需求也能 `search` 到它定下的规则 |
| 本工作区缺陷 | defects/ 里登记的缺陷 | `history find` 马上能查到，不用等缺陷系统下次导出 |

JSON 配置怎么拆表（表名 = 文件名/路径）：

| JSON 里的样子 | 拆成 | 查法示例 |
|---|---|---|
| 对象数组：`"gear": {"rod": [{"tier": 1, "price": 0}, …]}` | 表 economy/gear.rod，一个对象一行 | `cfg show economy/gear.rod --where tier=2` |
| 子项是结构相近的对象：`"species": {"jiyu": {"name": "鲫鱼"}, "liyu": {…}}` | 表 economy/species，一个子项一行，第一列“键” | `cfg show economy/species --where 键=jiyu` |
| 其余的单个数值：`"stamina": {"cap": 100, "regen": {"min": 5}}` | 表 economy/stamina，“键 / 值”两列，深层的写成 regen.min | `cfg show economy/stamina --where 键=cap` |

表名、字段名是英文时，表的目录卡片会给常见字段词配上中文（price=价格、unlock=解锁、tier=档位……），用中文 `cfg find 鱼竿 价格 解锁` 也能找到；项目自己的缩写（比如 rod、rep）配不上，靠知识库写清“数值在哪张表哪个字段”，或用 `cfg list rod` 按表名找。

要看某份资料的全文（比如 AI 更新知识库时读新文档），用 `qa.py index show 文件名`：读的是索引里转好的文字，Word、PDF 也能看。

## 怎么用

```
qa.py corpus add D:\项目\策划案 --kind doc --name 策划案
qa.py corpus add D:\项目\配置表 --kind config --name 配置表
qa.py corpus add D:\项目\缺陷导出 --kind defect --name 缺陷
qa.py index                      第一次全量建，之后只处理变化的文件
qa.py index stats                看概况
qa.py search "营业款 翻倍 封顶"
qa.py cfg find 鱼竿
qa.py cfg show 装备/鱼竿 --where name=龙骨巨物竿 --cols id,name,price
qa.py history find "回包丢失 重复到账" --module 营业款
qa.py history stats
qa.py index show 25_塘主经营改版设计.docx
```

资料文件夹有变化时，`qa.py status` 会提示“资料索引要更新”，再运行一次 `qa.py index` 即可。

认不出列的缺陷导出，在工作区 `qa.config.json` 里加：

```json
"defect_columns": { "title": "问题名称", "module": "功能分类", "severity": "级别" }
```

可以指定的字段：id、title、module、severity、status、desc、created、version、resolution。

## 向量检索（本地模型）

关键词检索不花钱、不用装东西，精确名词（规则名、道具名、缺陷标题）找得很准。向量检索补的是“意思相近但用词不同”的情况，比如问“把店里攒的钱加倍领”也能找到写着“营业款翻倍”的段落。两路结果按分数加权合并（向量默认权重 1.5，可在 `embedding.weight` 里改），关键词明确命中的不会被挤掉。

在钓鱼塘 44 份真实设计文档（切成 741 段）上的实测，本地 bge-m3：

| 检索方式 | 换了说法的 10 个问题：第 1 名就对 | 平均倒数排名 | 用原词的 8 个问题：第 1 名就对 |
|---|---|---|---|
| 只用关键词 | 4/10 | 0.57 | 8/8 |
| 关键词 + 向量（权重 0.6） | 5/10 | 0.65 | 8/8 |
| 关键词 + 向量（权重 1.5，默认） | 6/10 | 0.75 | 8/8 |
| 只用向量 | 7/10 | 0.80 | 没测 |

结论：向量检索对“换说法”的问题帮助很大；合并后精确词一个没丢。741 段文档算向量 15 秒，第一次调用要几秒加载模型。

接本地模型（资料不出本机、不花钱）：

1. 到 https://ollama.com 下载安装 Ollama。想装到别的盘：`OllamaSetup.exe /DIR="D:\Ollama"`；模型默认放在 C 盘用户目录，想放别的盘就先设用户环境变量 `OLLAMA_MODELS`（例如 `D:\OllamaModels`），再启动 Ollama
2. 在终端里运行 `ollama pull bge-m3`（中文效果好的向量模型，约 1.2 GB）
3. 在工作区里运行：`qa.py embed set ollama --model bge-m3`，再 `qa.py embed test` 试一下
4. `qa.py index` 补算向量

注意：Ollama 运行时会占 1～2 GB 内存。内存紧的电脑，算完向量后把 Ollama 退出；检索时要用向量才需要它开着，没开时框架自动只用关键词检索。

也可以接公司内网或云端的向量接口（OpenAI 兼容）：`qa.py embed set openai --model 模型名 --url https://…/v1 --key-env 密钥环境变量名`。

## 实测（框架作者在一台 Windows 电脑上测的）

造了一批和真实项目同量级的资料：300 份 Word 策划案、100 个 Excel 配置文件（500 张表、15 万行）、1 万条缺陷（禅道 GBK 编码的 CSV + Jira 英文表头的 Excel）。

| 项 | 结果 |
|---|---|
| 第一次建索引 | 402 个文件 90 秒；切出 1801 段文档；索引文件约 140 MB |
| 改一份策划案后增量更新 | 只处理 1 个文件，0.7 秒 |
| 检索、找表、查表、查缺陷 | 每次约 1 秒 |
| 准确度 | 埋进去的特定规则、道具、缺陷都排在第 1 名 |
| 缺陷列识别 | 禅道和 Jira 两种表头都自动认对 |

这一组大规模测试用的是测流程的“假向量”（随机造的资料没有真实语义）；真实向量模型的效果见上一节在真实设计文档上的对比。

## 局限

- 扫描版 PDF、图片里的文字读不出来（要先 OCR）
- Word 里的流程图、截图不进索引
- 一个配置文件里格式特别乱的表（多层合并表头），表头可能认偏，用 `cfg show` 看一眼就知道
- 资料到几万份以上时，建议把索引换成专门的检索服务（框架的检索接口不变）
