# 第 4 步：生成知识库并人工审核

**谁做**：AI 生成，用户审核。不用一次做完：先建模块清单，再按模块分批整理。

1. AI 运行 `{{qa}} prompt wiki-build`，照打印出来的任务说明做。第一次会先建 **模块清单**（`wiki/模块清单.md`），建好就停下来请用户审：
   - 模块：全项目统一的叫法，粒度到“一个人能讲清规则”（例如“渔具店”“营业款”）
   - 上级模块：缺陷系统、需求单里常用的大模块（例如“经营”）
   - 别名：别人可能怎么叫它（缺陷系统里的模块名、口头叫法、代码目录名），顿号隔开。以后谁写哪种叫法，框架都能统一成标准名
2. 用户确认清单后，AI 挑优先级最高的一批模块（不超过 5 个：缺陷多的、近期要改的、评审中的需求涉及的）整理：模块页、**耦合关系表**、风险清单、目录和变更记录
3. AI 运行 `{{qa}} wiki check`（格式：每页有来源、引用的资料都在、目录齐全、多模块时有耦合关系表、模块页都在清单里、别名不重复、过时登记能对上原文）和 `{{qa}} coupling`（看耦合表读得对不对），有问题就修
4. 停下来请用户审核。重点看三样：
   - 模块页的规则对不对（每条都标了出自哪份资料，可以对着查）
   - 耦合关系表有没有漏：哪些数值会被好几个模块同时改（价格、金币、次数、库存、体力……），约束写对没有
   - “待确认”的地方，用户能答的当场答掉
5. 用户说可以后：`{{qa}} wiki commit -m "整理模块：……"`。剩下的模块以后分批做：`{{qa}} prompt wiki-build`（接着做下一批）或 `--module 模块名`（指定）。`{{qa}} status` 和 `{{qa}} modules` 会显示“已整理几个 / 一共几个”

**为什么要耦合关系表**：AI 按需求出测试点时，容易只测需求里写到的那个模块。比如“购买”测得很全，却没想到“打折券”也会改价格，叠加后价格变负。有了这张表，框架会把相关模块一起交给 AI，生成后还会检查有没有漏（见 [架构说明](../架构.md) 的“耦合”一节）。

**新项目第一个需求就来了、知识库还空着**：也能先出测试点（靠资料索引检索），框架会提示缺哪些模块页；出完再把涉及的模块整理进知识库。

**做完的标准**：提交过一次知识库（哪怕只整理了一批模块）。
