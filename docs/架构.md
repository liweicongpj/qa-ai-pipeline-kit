# 架构与运作

## 一句话

把“测试知识 → AI 出测试点 → 人审 → 接口自动化 → 缺陷回流”做成一条有记录、可度量、能换模型的流水线。AI 负责干活，脚本负责判断对错和记账，人负责拍板。

## 三层结构

```
┌──────────────────────── 框架仓库（可以公开，所有项目共用）────────────────────────┐
│ qa.py + qakit/ 命令行：进度、导入、检查、审核、定稿、需求变更、缺陷、自动化、回归、指标 │
│ qa_index.py    资料索引：文档检索（关键词 + 向量）、配置表精确查、历史缺陷           │
│ qa_models.py   模型接入：Claude（官方 SDK）/ OpenAI 兼容 / Gemini / 命令行工具 / 假模型 │
│ prompts/       每一步交给 AI 的任务说明      templates/   工作区模板                   │
│ docs/          上手步骤、日常、架构           examples/    示例项目（含能本地跑的服务）  │
└──────────────────────────────────────────────────────────────────────────────────┘
                 │ init 生成            ▲ 每个命令都读写工作区
                 ▼                      │
┌──────────────────── 项目工作区（私有，每个项目一个，自己的 git 仓库）────────────────────┐
│ raw/ → wiki/ → reqs/R001/ → autotest/ → defects/ → metrics/                              │
│ qa.config.json（被测服务、各步骤默认模型、钩子）  AGENTS.md（工作区里 AI 的规则）          │
└──────────────────────────────────────────────────────────────────────────────────┘
                 ▲ 读文件、跑命令                         │ HTTP
                 │                                        ▼
         执行者：任意 AI 编程工具              被测服务（一个或多个，本地或测试环境）
   （Claude Code / Codex / Gemini CLI / Cursor）
     或 qa.py 直接调模型接口（gen / bench）
```

- **框架和工作区分开**：框架升级只要 `git pull`，不动项目资料；一个框架可以管多个项目
- **执行者可替换**：任何能读文件、跑命令的 AI 工具都能按 AGENTS.md 干活；不会跑命令的 AI（网页聊天）也能用，用户代跑命令、贴回输出
- **状态全在文件里**：知识库、测试点、审核、缺陷都是 Markdown，进 git；`.qa/` 里是进度、资料来源、模型调用记录。换一个 AI、换一个人接手，`status` 一跑就知道做到哪

## 一个需求走完一圈

```
资料 ──ingest──▶ raw/ ──AI 整理──▶ wiki/（模块页 · 耦合关系表 · 风险清单）──人审──▶ wiki commit
                                         │
需求 ──req new──▶ reqs/R001/需求.md      ▼
        AI 出测试点（prompt testpoints 或 gen / bench）──▶ 测试点.md
                                         │  框架查耦合关系表：共用数值没测到 → 提醒
                                         ▼
                      review ──▶ 审核.md ──人逐条审──▶ accept ──▶ 最终测试点.md + 指标
                                         │  AI 把新规则、新耦合并进知识库（prompt wiki-merge）──人审──▶ wiki commit --merged
                                         │
        AI 出用例清单（含两两组合、不变量）──人审──▶ AI 写 pytest ──▶ autotest run
                                         │  每个用例结束自动查不变量
                                         ▼
                      失败 ──AI 归因──人确认──▶ defect new ──▶ 漏测？
                                                              │是
                                         AI 把规律写回风险清单 / 耦合关系表 ──人审──▶ wiki commit --feedback
                                                              │
                                         下一个需求生成测试点时用上（闭环）
```

## 自动化做到什么程度

| 环节 | 谁做 | 自动化程度 |
|---|---|---|
| 环境检查、建工作区、目录和模板 | 框架 | 全自动 |
| 导入资料、记来源、资料变化检测 | 框架 | 全自动（`ingest --refresh` 一键刷新） |
| 大批资料建索引、增量更新、检索、查表 | 框架 | 全自动（资料变了 status 会提示重建） |
| 整理知识库、增量更新 | AI | 自动生成，**人审后提交** |
| 资料文件夹文档变了、需求定稿了，提醒更新知识库 | 框架 | 全自动（status 提示） |
| 把定稿需求的新规则并进知识库 | AI | 自动整理，**人审后提交** |
| 模块名统一（别名、大模块）、推荐需求涉及的模块 | 框架 | 全自动（推荐，人确认） |
| 需求原文改了：检测、对比 | 框架 | 全自动 |
| 需求改了：要改的测试点 + 要回归的原有功能 | AI | 自动生成，**人只审变动** |
| 配置晚到、配置改了：提醒校对 | 框架 | 全自动；校对由 AI 做、人确认 |
| 过时规则：检索结果里标到那一句 | 框架 | 全自动（登记由 AI 做、人审） |
| 版本回归清单、自动化部分填结果、回归报告 | 框架 | 全自动；手工部分人执行 |
| 知识库格式检查（来源、引用、目录、耦合表） | 框架 | 全自动 |
| 出测试点 | AI | 自动生成，**人逐条审核** |
| 耦合遗漏提醒 | 框架 | 全自动（查表对照，提醒不拦截） |
| 定稿、采纳率 / 编造 / 补充统计 | 框架 | 全自动 |
| 两两组合 | 框架 | 全自动（算法生成，不靠 AI） |
| 接口用例清单 | AI | 自动生成，**人审清单** |
| 写用例代码、不变量 | AI | 自动生成，**人看断言** |
| 跑用例、启动关闭服务、和上次对比 | 框架 | 全自动（可挂 CI / 定时任务） |
| 不变量检查 | 框架 | 每个用例结束后全自动 |
| 失败归因 | AI | 自动分析，**人确认** |
| 缺陷登记 | 人 / AI | 半自动（模板、自动带模块和用例） |
| 回流进知识库 | AI | 自动整理，**人审后提交** |
| 指标、模型用量、选型报告 | 框架 | 全自动 |
| 失败后改了用例却没写归因的提醒 | 框架 | 全自动 |
| 提交、推送到项目仓库 | 框架 | 全自动（设了项目仓库后；第一次要人登录） |

原则：**AI 写，脚本判，人拍板。** 资产守不守恒、价格是不是负数、次数有没有超，都由确定性的断言和不变量判断，不让模型说“对”或“不对”。

## 解决什么问题

| 问题 | 怎么解决 |
|---|---|
| 测试知识在人脑子里，人一走就丢 | 知识库带出处、进 git；漏测回流写回去，越用越全 |
| AI 出的测试点不知道靠不靠谱 | 每条人审，留记录；采纳率、编造数、补充数量化 AI 的表现 |
| AI 会编规则 | 只许用知识库里有的规则，每条标依据；否决原因“不符合规则”单独统计 |
| 只测了需求写到的模块，漏了模块之间的叠加 | 耦合关系表 + 生成时带上相关模块 + 漏测提醒 + 两两组合 + 不变量兜底 |
| 回归压力大 | 接口自动化一条命令跑完，和上次比新失败、修好 |
| 用例断言写错没人发现 | 人审断言；不变量独立于用例，换个角度再查一遍 |
| 不知道该用哪个模型、花了多少钱 | 每次调用记 token、耗时、费用；bench 盲审对比；各步骤可配不同模型 |
| 换了 AI 工具或换了人就接不上 | 进度和产物都在文件里，`status` 告诉任何人下一步 |

## 资料量大时：检索层

真实项目的资料（几百份策划案、几千张配置表、成千上万条缺陷）放不进提示词。框架分两层：

- **资料索引**（`.qa/index.sqlite`，不进 git）：资料留在原处，框架建索引并增量更新。策划文档切段后用关键词 + 向量检索；配置表（Excel、CSV、JSON）建表目录、精确查值；历史缺陷自动识别各系统的列，按模块检索和统计。本工作区做过的需求和登记的缺陷也自动进索引
- **知识库**（`wiki/`）：只放精华（规则、口径、耦合、风险），AI 借助检索按模块分批整理；不抄配置数值，只写数值在哪张表哪个字段

生成测试点时，AI 工具用 `search`、`cfg show`、`history find` 查资料；框架直接调模型时，自动把检索到的策划段落、同类历史缺陷和相关配置表放进提示词，支持工具调用的模型还能自己再调这些只读工具查（查表时可以顺着关联字段一张张查下去）。详见 [大批资料与检索](大批资料与检索.md)。

## 模块之间的耦合怎么查

例子：商城“购买”的用例 AI 给得很全，但没考虑“打折券”。真实环境里，叠加打折券以后成交价变成负数。框架用四道机制管这类问题，从“设计时想到”到“运行时兜底”：

1. **知识库里的耦合关系表**（wiki/耦合关系.md）：列出被多个模块共用的数值，谁会改、谁会读、约束是什么。例：`| 成交价 | 商城、打折券、会员 | 订单、对账 | 不能小于 0 |`。生成知识库时 AI 整理，人审
2. **出测试点时带上相关模块**：需求标了模块“商城”，框架查表发现“成交价”也被“打折券”“会员”改，把这些模块的知识页和约束一起交给 AI，要求写“耦合”类测试点
3. **漏测提醒**：测试点生成后、审核时、定稿时，框架对照耦合关系表检查：类型为“耦合”的测试点（或审核时人工补充的）里，共用的数值、它的关键词或相关模块一次都没出现，就提醒（`coupling R001` 随时看）。只看“耦合”类，是因为普通测试点的依据里也常引用别的模块页，算进来会漏报（钓鱼塘试跑时实测过）
4. **两两组合**：把相关因素列出来（商品价 0 / 1 / 500 / 3000 × 无券 / 满减券 / 折扣券 / 两张叠加 × 会员否 / 是 × 数量 1 / 2 / 99），全组合 96 种，`combos` 生成约 16 种就能覆盖任意两个因素的所有搭配
5. **不变量兜底**：约束写成 autotest/invariants.py（成交价 ≥ 0、金币 ≥ 0、金币 = 初始 + 流水合计），每个用例结束后自动查。哪怕谁都没想到“打折券 + 会员价”这个组合，只要某个用例走到了负价格，这个用例就会失败

查不出来的情况：耦合关系没写进资料、也没人想到，而且没有任何用例走到那个状态。补救：漏测缺陷归类填“耦合”，回流时补进耦合关系表，下次同类需求就会提醒。

## 多模型

- **两种用法**：工作区里的 AI 工具直接干活（用工具自己的模型），或者 `gen <步骤>` / `bench` 由框架直接调模型接口（每一步都能；能精确记 token 和费用）。正式部署走后一种，见 [自动流转](自动流转.md)
- **多模型结合**：`qa.config.json` 的 `stage_models` 给不同步骤配不同模型，比如出测试点用强模型、归因用便宜模型
- **选型**：`bench` 同一份输入给几个模型，顺序打乱盲审，`bench report` 揭晓：采纳率、编造、补充、token、耗时、费用、每条采纳测试点的成本
- 详见 [多模型与选型](多模型与选型.md)

## 三种环境

| 环境 | 能做什么 | 做不了的 |
|---|---|---|
| 无代码权限 | 知识库、测试点、审核、手工执行记录、缺陷回流、指标；能抓包时把 HAR 整理成接口文档，再做接口自动化 | 没有接口也抓不到包时，自动化只能靠界面自动化工具（框架外） |
| 开放接口或协议 | 上面全部 + 接口自动化（HTTP、TCP、WebSocket，协议客户端由 AI 按协议文档写） | 看不到代码，耦合关系只能从文档和缺陷里整理 |
| 完整代码权限 | 上面全部 + 对照代码核对规则、从代码补耦合关系、按 git 改动推荐回归范围、本地起服务或写桥接 | — |

## 多系统

- **操作系统**：框架只用 Python 标准库加少量包，Windows / macOS / Linux 都能跑；GitHub Actions 在三个系统上跑自检
- **自己公司的服务器**：被测服务就是一个地址（本机、测试服、预发、云上都行），一直在跑的服务不用配启动命令
- **多个被测服务**：一个项目可以配多个 target（网关、游戏服、支付服、运营后台、不同环境……），用例、接口文档、运行记录分开
- **多个项目**：每个项目一个工作区，`use` 切换；需求、缺陷、指标按功能模块归类

## 扩展

提示词、模板可以按项目覆盖；风险分类、模块、被测服务、钩子都在配置里；新模型接口加一个 provider 函数即可。详见 [扩展](扩展.md)。

## 局限

- 知识库的质量取决于资料和人审；资料错了，AI 会照错的出
- 测试点覆盖率没有绝对标准，靠漏测回流慢慢逼近；样本少时指标只能看趋势
- 接口自动化只覆盖能通过接口验证的部分；界面、手感、性能要别的工具
- 模型接口的 token 和费用以接口返回为准；命令行工具的用量取决于它是否输出（claude 会输出，其他工具可能没有）
- 公司内部资料能不能发给外部模型，要按公司规定；可以接内网部署的模型（OpenAI 兼容接口或 Ollama）
