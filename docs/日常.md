# 日常用法

上手完成后，每次开工还是先 `{{qa}} status`，它会列出所有待办。常见场景：

## 来了新需求

1. `{{qa}} req new "标题" --from 需求文件 --module 模块1,模块2`
2. 生成测试点：`{{qa}} prompt testpoints R00X`（工作区里的 AI 做）或 `{{qa}} gen testpoints R00X --model <模型>`
3. `{{qa}} review R00X` → 人审 → `{{qa}} accept R00X`
4. 接口能测的：`{{qa}} prompt tests-plan R00X` → 人审清单 → `{{qa}} prompt tests-write` → `{{qa}} autotest run`

## 项目资料改了

`{{qa}} ingest --refresh` → `status` 会提示“知识库要更新” → `{{qa}} prompt wiki-update` → 人审改动 → `{{qa}} wiki commit -m "说明"`

## 发现了缺陷（测试中或线上）

1. `{{qa}} defect new "标题" --req R00X --stage 测试|线上`，填严重程度、是否被最终测试点覆盖、归类、现象、原因
2. 没被覆盖的就是漏测，`status` 会提示待回流 → `{{qa}} prompt feedback` → AI 把规律写回风险清单 / 耦合关系表 → 人审 → 按提示 `wiki commit --feedback D00X`
3. 以后同类需求生成测试点时，就会用上这次的教训

## 版本回归

`{{qa}} autotest run --start`（多个服务就每个 `--target` 跑一遍）。摘要会和上次比：新失败、修好了哪些。失败的先归因再登记缺陷。

可以把它挂到 CI 或定时任务上；`qa.config.json` 的 `hooks.after_autotest` 可以配一条命令（比如发通知），跑完自动执行。

## 选模型、比成本

- `{{qa}} bench testpoints R00X --models a,b,c`：同一份输入给几个模型，盲审后 `bench report` 揭晓，对比采纳率、编造、补充、token、耗时、费用
- `{{qa}} usage`：所有模型调用的 token、耗时、费用，按模型、按步骤汇总
- 详见 [多模型与选型](多模型与选型.md)

## 看效果

`{{qa}} metrics` → metrics/指标.md：每个需求和每个模块的采纳率、编造、补充、漏测率，缺陷回流情况，自动化运行情况，模型用量。
