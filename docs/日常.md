# 日常用法

每次开工先 `{{qa}} status`，它会列出所有待办（需求改了、配置变了、接口到了、该回流了……都会提醒）。下面按实际开发流程说每个阶段跑什么。

## 情况一：新功能（策划先写需求文档）

| 阶段 | 跑什么 | 谁做 |
|---|---|---|
| 需求文档出来（评审前） | `{{qa}} req new "标题" --from 需求文档 --module 模块`（模块不确定就不写，框架会按内容推荐）→ `{{qa}} prompt testpoints R00X` | 人导入，AI 出测试点 |
| 需求评审会 | 带上 测试点.md 末尾的“需要和策划确认的问题”，会上问掉 | 人 |
| 评审后定稿 | `{{qa}} review R00X` → 人审 → `{{qa}} accept R00X` → `{{qa}} prompt wiki-merge R00X`（新规则并进知识库）→ 人审 → `wiki commit --merged R00X` | 人审，AI 整理 |
| 开发中：需求改了 | `status` 提醒“原文件改过了” → `{{qa}} req refresh R00X` → `{{qa}} prompt req-change R00X`（AI 出要改的测试点 + 受影响要回归的原有功能）→ `review` → `accept` | 人审，AI 出变更 |
| 开发中：接口还没出 | `{{qa}} prompt tests-plan R00X` 照样能做：先出用例清单和骨架（标“等接口”跳过）；接口文档到了 `ingest --api`，`status` 提醒补全 | AI 写，人审清单 |
| 配表（开发中或开发后） | 测试点里没出的数值先写“待配表”；配置进了资料文件夹 → `{{qa}} index` → `status` 提醒校对 → `{{qa}} prompt cfg-check R00X` → 人看 → `{{qa}} req cfg-checked R00X` | AI 校对，人确认 |
| 提测 | 能调接口的：`{{qa}} autotest run --start`；只能手工的：`{{qa}} exec R00X --round 提测1` 按清单测、填结果 | 框架跑 / 人测 |
| 有失败 | `{{qa}} prompt triage` → AI 归因 → 人确认 → `{{qa}} defect new "标题" --req R00X` | AI 分析，人确认 |
| 策划验收、上线后 | 漏测的缺陷 → `status` 提醒待回流 → `{{qa}} prompt feedback` → 人审 → `wiki commit --feedback D00X` | AI 整理，人审 |

最早、最值钱的是第一行：需求文档一出来就出测试点，不用等开发、配表、接口。需求里的矛盾（比如“第四档要口碑 150，但口碑上限只有 100”）在评审会上就能提出来。

## 情况二：旧功能修改、新增规则（策划直接在缺陷系统里提需求单）

1. 把需求单导出（网页、Excel 都行；只能看网页的就把单子文字复制成一个 .md）
2. `{{qa}} req new "标题" --from 需求单文件 --module 模块`：需求单上的“所属模块”太大、太模糊的，直接写上也行（框架认得出是大模块，会在它下面推荐具体模块），或者不写让框架推荐
3. `{{qa}} prompt testpoints R00X`：知识库里有这个功能现在的规则，AI 会拿新单子对照旧规则，重点写“改了什么”和“回归”类测试点（改动后原来哪些功能必须还对），以及改动连带影响到的模块（耦合表）
4. 完整代码权限下，开发提交后 `{{qa}} impact --range 上个版本..这个版本`，按代码改动推荐回归范围
5. 后面同情况一。**定稿后一定要 `prompt wiki-merge`**：没有需求文档，新规则只存在于需求单里，不并进知识库，下次就没人知道了

需求单在缺陷系统里改了：重新导出覆盖原文件（或另存一个文件用 `req refresh R00X --from 新文件`），走“需求改了”那一行。

## 老项目中途接入

1. 建工作区，选环境（无代码 / 开放接口 / 完整代码）：`{{qa}} init <文件夹> --name 项目名 --access …`
2. 登记全部资料，资料留在原处：
   - 策划文档：`{{qa}} corpus add <文件夹> --kind doc`
   - 配置表（Excel / CSV / JSON）：`--kind config`
   - 缺陷系统导出：`--kind defect`
   - 以前写的测试用例表：当文档登记（`--kind doc`），整理风险清单时会参考；版本回归时还能拼进回归清单
3. `{{qa}} index` 建索引（几百份资料几分钟），有本地向量模型的先开好
4. 建知识库：先 `{{qa}} prompt wiki-build` 建模块清单（从缺陷系统的模块名、文档目录、代码目录整理），人审；再按优先级分批整理模块。不用等全部整理完，新需求涉及哪个模块就先整理哪个
5. 已有的接口自动化用例可以放进 autotest/tests/，用 `autotest run` 统一跑和记录

## 资料有变化

- 资料文件夹里加了、改了文件：`status` 提醒“资料索引要更新” → `{{qa}} index`（只处理变化的文件）
- 文档类资料变了：`status` 还会提醒“知识库可能要更新” → `{{qa}} prompt wiki-update` → 人审 → `wiki commit`
- raw/ 里的资料：`{{qa}} ingest --refresh` → 同上
- 缺陷系统定期导出：覆盖登记文件夹里的同名文件 → `{{qa}} index`
- 资料里的旧规则已经不用了：AI 在并入新规则、更新知识库时登记进 `wiki/过时资料.md`（精确到那一句），检索时紧跟在那段原文后面标“已过时”，同一节、同一行里还在用的规则照常

## 日常回归和版本回归

**每天回归（能调接口的环境）**：

```
{{qa}} autotest run --start
```

自动启动被测服务、跑全部用例、和上次对比“新失败了哪些、修好了哪些”，每个用例结束自动查不变量。可以挂到 Windows 任务计划或 Jenkins 上定时跑；`qa.config.json` 的 `hooks.after_autotest` 可以配一条命令（比如发通知），跑完自动执行。

**版本回归**：

1. 拼回归清单：`{{qa}} regress new v1.3 --modules 装备,自家塘经营 --level 高,中 --cases 旧用例.xlsx`
   - 从所有定稿需求的最终测试点里，按模块和风险等级挑；以前写的 Excel / CSV 用例也能拼进来（自动认出用例标题、模块、优先级，P0–P3 也认）
   - 写自动化用例时在文档字符串里写上对应的测试点编号（如 `R002-T03`），清单里就会标出哪条有自动化
2. `{{qa}} regress run v1.3 --start`：跑清单里有自动化的那部分，结果自动填进清单
3. 其余照清单手工执行，填结果；失败的先登记缺陷，把编号填进来
4. `{{qa}} regress check v1.3`：检查有没有漏填，出 回归报告.md（通过率、按模块统计、失败和阻塞清单、和上一轮比）

完整代码权限时，可以先用 `{{qa}} impact --range v1.2..v1.3` 看代码改动影响到哪些模块，再用 `--modules` 拼清单。

框架只测到接口这一层，不驱动游戏客户端；客户端界面回归要另接工具，可以通过 hooks 挂进来。

## 选模型、比成本

- `{{qa}} bench testpoints R00X --models a,b,c`：同一份输入给几个模型，盲审后 `bench report` 揭晓，对比采纳率、编造、补充、token、耗时、费用
- `{{qa}} usage`：所有模型调用的 token、耗时、费用，按模型、按步骤汇总
- 详见 [多模型与选型](多模型与选型.md)

## 上传到项目仓库

工作区默认只在本地。要让资料、知识库、测试点、用例和运行结果自动上传：

1. 为这个项目建一个**私有**仓库（GitHub 私有仓库、公司 GitLab 都行），不要用框架仓库
2. `{{qa}} remote set <仓库地址>`：设好以后，`accept`、`wiki commit`、`autotest run`、`metrics` 提交后会自动推送
3. 第一次推送要登录：在你自己的终端里运行 `{{qa}} sync`，按弹窗登录。之后自动推送就不用再登录了
4. 推到 GitHub 前，建议在工作区里把提交邮箱设成 GitHub 的隐藏邮箱：`git config user.email <Settings → Emails 里的 noreply 地址>`

自动推送失败（比如没登录、断网）不会影响本地提交，框架会提示你手动 `{{qa}} sync`。

## 回答待确认

`{{qa}} wiki todo` 列出知识库里所有待确认的问题（不算标题、目录、变更记录，重复的只算一次）。能回答的告诉 AI，让它改进知识页、删掉那一条，再 `wiki commit`。

## 看效果

`{{qa}} metrics` → metrics/指标.md：每个需求和每个模块的采纳率、编造、补充、漏测率，缺陷回流情况，自动化运行情况，模型用量。
