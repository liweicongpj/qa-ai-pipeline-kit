# 自动流转：正式部署时怎么接

上手和搭建可以让 AI 工具带着做；正式运行时一般放在一台专门的电脑或服务器上，由 SVN 钩子、禅道、Jenkins 触发，
每一步都由框架**直接调模型**（`qa.py gen <步骤>`），旁边不需要开着 AI 工具。人只在审核的地方出场。

## 部署

- 一台常开的机器：放框架、项目工作区（工作区自己是一个 git 仓库，可以 `remote set` 自动推到项目私有仓库）
- 向量模型常开（比如本机 Ollama + bge-m3），检索才快、才准
- 模型密钥放这台机器的环境变量；`models.local.json` 登记模型，工作区 `qa.config.json` 的 `stage_models` 给每一步配模型（可以写列表：前一个失败用下一个，见 [多模型与选型](多模型与选型.md)）
- 资料目录指向 SVN 检出的文件夹（框架只看文件，不管它是 SVN 还是共享盘）

## 每一步现在能不能无人跑

| 步骤 | 命令 | 做完停在哪 |
|---|---|---|
| 导入需求 | `req new "标题" --from 需求文件 --module 模块` | — |
| 资料有变化 | `index`（增量） | — |
| 出测试点 | `gen testpoints R001 --review` | 审核表等人审（触发 `after_review_ready`） |
| 人审完定稿 | `accept R001`（人填完审核表后运行，或由网页 / 机器人代为运行） | 定稿（触发 `after_accept`） |
| 新规则并进知识库 | `gen wiki-merge R001` | 知识库改动等人审，人确认后 `wiki commit --merged R001` |
| 需求原文改了 | `req refresh R001` → `gen req-change R001` | 变更审核表等人审（触发 `after_review_ready`） |
| 配置表出来或改了 | `gen cfg-check R001` | 改动等人确认，确认后 `req cfg-checked R001` |
| 资料变了更新知识库 | `gen wiki-update` | 知识库改动等人审 |
| 用例清单 | `gen tests-plan [R001]` | 清单等人确认 |
| 写用例代码 | `gen tests-write` | 代码已能被 pytest 收集，等人看断言 |
| 跑接口用例 | `autotest run --start --exit-code` | 有失败时退出码 1（Jenkins 标红） |
| 失败归因 | `gen triage` | 归因等人确认，真缺陷 `defect new` |
| 漏测回流 | `gen feedback` | 知识库改动等人审 |

每次 `gen` 做完会触发 `after_gen` 钩子（带上这一步、成没成功、写了哪些文件），可以挂通知脚本。

## 三条线

**策划提交了需求文档（SVN）**

SVN 的提交后钩子（post-commit）去触发一个 Jenkins 任务，任务里：

```
svn update 资料目录
python qa.py --ws 工作区 index
python qa.py --ws 工作区 req new "需求标题" --from 资料目录/新需求.docx --module 模块
python qa.py --ws 工作区 gen testpoints R00x --review
```

改的是已有需求的文档：`req refresh R00x`，再 `gen req-change R00x`。

**禅道里提的需求**

禅道可以配 Webhook，或者定时用禅道接口取新需求。把需求内容存成文件（Markdown 或导出的 Word），再走上面同样的 `req new --from`、`gen testpoints --review`。
（框架还没有内置禅道连接器，这一段要写一个小脚本。）

**每日回归（Jenkins 定时）**

```
python qa.py --ws 工作区 autotest run --start --exit-code
（失败时）python qa.py --ws 工作区 gen triage
```

## 通知审核人

在 `qa.config.json` 的 `hooks` 里挂脚本，例如审核表生成后发群消息：

```json
"hooks": { "after_review_ready": "python D:/tools/notify.py" }
```

脚本里读环境变量 `QA_REQ`（哪个需求）、`QA_REVIEW`（审核表路径），发到企业微信 / 钉钉 / 飞书机器人。其他钩子见 [扩展](扩展.md)。

## 等很久才来审、一人审多个需求

- 进度是按文件算的：有测试点没定稿就是“待审核”，等几天也不会重来；审核表填一半也保存着
- 每个需求一个文件夹，互不影响；一个人可以按任意顺序审多个需求
- 等的期间需求原文改了：`req refresh` 会对比新旧，只让人审变动的部分

## 失败了怎么办

| 情况 | 框架怎么做 |
|---|---|
| 限流、服务端 5xx、断网、超时 | 等一会儿重试（默认 2 次，等待时间翻倍） |
| 密钥不对、模型拒答、重试还不行 | 换 `stage_models` 里配的下一个模型 |
| 输出格式不对、检查没通过（测试点解析不出、知识库格式检查有新问题、用例代码收集失败、写了不该写的文件） | 把问题发回去让模型改（默认 2 轮）；还不行就保留结果、列出问题，退出码 1，等人看 |
| 任何一步失败 | 不会弄坏前面的成果：每一步的结果都是文件，状态按文件算，修好后同一条命令重跑就行 |

排查：工作区 `.qa/calls.jsonl` 记着每次调用（模型、token、费用、成没成功、查了几次资料），`.qa/gen/` 存着每次的提示词和输出。

## 还没有的（后续）

- 一个需求多人审（按模块分派审核人、全部审完才能定稿）、审核超时提醒
- 网页审核界面（现在审核表是 Markdown，可以在共享仓库里直接改）
- 禅道等系统的内置连接器
- `status --json` 的待办现在是给人看的句子，后续改成带类型的结构化数据，方便流水线判断下一步
