## 每次开工

1. 运行 `{{qa}} status`，看上手进度和待办
2. 运行 `{{qa}} next` 看下一件事的详细做法；某一步的具体任务用 `{{qa}} prompt <名字>` 打印出来，照着做
3. 一次只做一件事，做完向用户汇报，再做下一件

## 人工关口：到这些地方必须停下来，等用户

- raw/ 资料里的事实对不对、缺什么：问用户，不要自己补
- 知识库改动：提交前把改动摘要给用户看，用户说可以再运行 `wiki commit`
- 测试点审核表：结论（采纳 / 改后采纳 / 否决）、否决原因、修改内容、补充的测试点，全部由用户定。你可以一条条念给用户、照用户说的记，但不能替用户判断
- 接口用例清单：用户确认后才写代码
- 自动化失败的归因：你给判断和依据，用户确认后才登记缺陷
- 缺陷是否“被最终测试点覆盖”：用户判断
- 装软件、改被测项目的代码、动本文件夹以外的文件：先问

## 资料和知识库

- raw/ 只读，不要改；资料要更新用 `{{qa}} ingest`（会记下来源，以后 `ingest --refresh` 一键刷新）
- wiki/ 每页开头写“来源：raw/…”，每条规则后面标出自哪个文件
- 资料没写清楚的不要自己补规则，写进那一页末尾的“## 待确认”，一条一行，同一个问题只写一页；状态说明（未验收、待验证）不算待确认。`{{qa}} wiki todo` 列出全部待确认
- 数值计算（次数、封顶、价格、折扣、取整）写 Python 脚本算，不要心算
- 改 wiki 后在 wiki/log.md 记一行：日期、改了什么、为什么

## 大批资料（策划案、配置表、历史缺陷）

资料多的项目，原始资料不复制进来，而是登记目录后建索引（`{{qa}} corpus add`、`{{qa}} index`）。这时：

- 找资料用 `{{qa}} search "关键词"`，不要直接翻整个资料文件夹，也不要试图一次读完；要看某份资料全文用 `{{qa}} index show 文件名`（Word、PDF 也行）
- 数值用 `{{qa}} cfg show 表名 --where 字段=值` 精确查，不要凭印象写（配置表支持 Excel、CSV、JSON）
- 历史缺陷用 `{{qa}} history find` / `{{qa}} history stats`
- 本工作区做过的需求（需求原文、最终测试点）和登记的缺陷会自动进索引，不用登记
- 知识库里不抄配置数值，只写规则、口径和“数值在哪张表哪个字段”
- 资料有变化时 `{{qa}} status` 会提示重建索引；资料文件夹里的文档变了，还会提示更新知识库

## 需求定稿以后

- 定稿（accept）后，把这个需求定下的新规则、新耦合并进知识库：`{{qa}} prompt wiki-merge 需求编号`，用户看过后 `wiki commit --merged 需求编号`。不并进来，以后的需求读知识库时还是旧规则

## 测试点

- 先读 wiki/index.md，再读相关模块页和 wiki/risks/风险清单.md
- 按 templates/测试点模板.md 的表头输出，每条注明依据的 wiki 页；文件第一行写 `<!-- 生成：工具和模型名，日期 -->`
- 不要读其他需求的审核表

## 接口用例

- 服务地址用 autotest/conftest.py 里的 base_url 夹具（读环境变量 {{url_env}}，没设就用 qa.config.json 的 target.base_url）
- 断言只用确定的计算；涉及金币、物品、次数、订单的，执行前后拍快照对账
- 用例失败时不要改用例去迁就服务；确实是用例写错了，先写归因（`{{qa}} prompt triage`），用户确认后再改
- 测试用的辅助代码（桥接、协议客户端、造数据脚本）放在本文件夹的 autotest/ 下，不要放进被测项目的仓库
- 自己手动启动的被测服务，用完要关；`autotest run --start` 会自动启动和关闭
- 跑用例用 `{{qa}} autotest run`（服务没在跑可加 --start），不要自己拼 pytest 命令：它会记录历史、和上次对比

## 提交

- `accept`、`wiki commit`、`autotest run`、`metrics` 会自动 git 提交；设了项目仓库（`{{qa}} remote set <地址>`）就提交后自动推送
- 其他改动（缺陷记录、用例、需求）做完一件事提交一次：`git add -A -- .` 然后 `git commit -m "说明" -- .`
