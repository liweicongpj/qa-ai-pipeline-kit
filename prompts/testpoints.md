任务：为需求 {{req}} 生成测试点。

环境：{{access_name}}。{{access_note}}

1. 读 {{req_dir}}/需求.md，先确认涉及哪些模块（现在标的：{{modules}}）：
   - 运行 `{{qa}} req modules {{req}}` 看框架按需求内容推荐的模块和理由；模块名以 wiki/模块清单.md 为准，需求单上写的大模块要落到具体模块
   - 定下来后运行 `{{qa}} req modules {{req}} --set 模块1,模块2`；改了模块就重新运行 `{{qa}} prompt testpoints {{req}}`，拿到最新的耦合提示
   - 涉及的模块知识库里还没有页的，先运行 `{{qa}} prompt wiki-build --module 那几个模块` 整理，用户审核提交后再回来出测试点
2. 读 wiki/index.md，再读相关模块页、wiki/耦合关系.md 和 wiki/risks/风险清单.md；不要读其他需求的审核表
   建了资料索引的（{{qa}} index stats 能看到），再查原始资料，别去翻整个资料文件夹：
   - `{{qa}} search "需求里的关键词"` 查策划文档里相关的段落（换几组关键词多查几次）；以前做过的需求（资料名“本工作区需求”）也在里面，同一个模块以前定下的规则要对照
   - `{{qa}} history find "关键词" --module 模块` 查同类历史缺陷（缺陷系统导出的和本工作区登记的都在），出过的问题要写进测试点
   - `{{qa}} cfg find "关键词"` 找涉及的配置表，`{{qa}} cfg show 表名 --where 字段=值` 查具体数值；数值以查到的为准，不要猜。配置还没出的写“待配表：要什么数值”
   - 资料互相打架时按这个顺序信：这次的需求原文 > 知识库 > 以前定稿的需求 > 原始资料。检索结果里标着“已过时”的句子不要用。冲突了不要自己挑一个，写进“需要和策划确认的问题”
   依据里可以写资料文件名和章节（例如“策划案/营业款设计.docx · 翻倍规则”），用到配置的写表名
3. 这个需求涉及的模块和别的模块共用这些数值（框架从耦合关系表查出来的）：
{{coupling}}
   对每个共用数值，都要写“耦合”类测试点：别的模块同时改它时的叠加顺序、上下限（约束）、取整、先后到达。别只测需求里写到的那一个模块
4. 改旧功能或加新规则的，要写“回归”类测试点：这次改动后，原来的哪些功能和规则必须还是对的
5. 按 templates/测试点模板.md 的表头输出到 {{req_dir}}/测试点.md，文件第一行写 `<!-- 生成：你的工具和模型名（例如 Claude Code / claude-opus-5-5），日期 -->`（框架靠它在审核表和指标里记下是哪个模型出的），第二行写“涉及模块：……（理由）”：
   - 每条一个风险点，写清怎么验证（界面/日志/数据库/对账）
   - 依据写具体的 wiki 页；风险清单里适用的类别都过一遍
   - 按风险从高到低排序
6. 表格后面另起一节“需要和策划确认的问题”：需求里没写清楚的边界、和现有规则冲突的地方
7. 运行 {{qa}} review {{req}} 生成审核表（它会顺带检查耦合有没有漏）
8. 停下来：告诉用户审核表在 {{req_dir}}/审核.md，请用户逐条填结论。不要替用户填。用户填完后运行 {{qa}} accept {{req}}
